# 🚂 12306 全网仿真后端 API 规范 (Node.js/Express)

## 1. 核心目标
构建一个覆盖中国主要地理区域、全车次类型、全席别的仿真铁路数据库。通过算法自动生成数千条车次数据，支持任意两个城市间的查询及高级筛选。

## 2. 数据库表设计 (Schema: `tickets`)

| 字段名 | 类型 | 描述 |
| :--- | :--- | :--- |
| `id` | INTEGER | 主键 |
| `train_no` | TEXT | 车次号 (如 G101, Z5, K336) |
| `train_type`| TEXT | 类型代码 (G/D/Z/T/K) |
| `start_station`| TEXT | 出发站 (精确，如 "上海虹桥") |
| `end_station` | TEXT | 到达站 (精确，如 "北京南") |
| `from_city` | TEXT | 出发城市 (用于搜索，如 "上海") |
| `to_city` | TEXT | 到达城市 (用于搜索，如 "北京") |
| `start_time` | TEXT | 出发时间 (HH:MM) |
| `end_time` | TEXT | 到达时间 (HH:MM) |
| `duration` | TEXT | 历时 (HH:MM) |
| `date` | TEXT | 发车日期 (YYYY-MM-DD) |
| **全席别库存** | | **状态值：'有', '无', '1-20数字', '候补'** |
| `swz` | TEXT | 商务座/特等座 (仅 G/C) |
| `yd` | TEXT | 一等座 (仅 G/C/D) |
| `ed` | TEXT | 二等座 (仅 G/C/D) |

## 3. 接口定义 (`GET /api/tickets`)
支持以下参数：
* `date`, `from`, `to` (基础查询)
* `filterType` (车型筛选，如 "G,D")
* `filterStationIn/Out` (精确车站筛选)
* `filterTimeStr` (时间段筛选，如 "06:00-12:00")

## 4. 全网数据生成策略 (Procedural Generation Strategy) - 🚨 核心逻辑

服务启动时 (`server.js`) 必须运行生成算法，基于以下规则填充内存数据库：

### A. 基础数据字典 (City Dictionary)
代码需内置一个覆盖全国的大型城市映射对象 `CITY_MAP`，必须包含以下区域的代表城市：
* **华北:** 北京(北京南/北京西/北京), 天津(天津西/天津), 石家庄, 太原
* **华东:** 上海(虹桥/南/上海), 杭州(东/城站), 南京(南/南京), 苏州, 济南, 福州, 厦门
* **华南:** 广州(南/东/白云), 深圳(北/罗湖), 南宁, 海口
* **华中:** 武汉(汉口/武昌/武汉), 长沙(南/长沙), 郑州(东/郑州)
* **西南:** 成都(东/南), 重庆(北/西), 昆明, 贵阳
* **西北:** 西安(北/西安), 兰州(西/兰州), 乌鲁木齐
* **东北:** 沈阳(北/沈阳), 哈尔滨(西/哈尔滨), 长春

### B. 车次生成逻辑 (Train Logic)
编写 `generateMockData()` 函数，遍历城市列表进行**两两组合** (Pairwise Generation)：

1.  **车次密度权重:**
    * **一线城市互通** (如北京-上海, 广州-深圳): 生成 20-40 趟车。
    * **省会互通** (如西安-成都, 武汉-长沙): 生成 10-15 趟车。
    * **普通连接**: 生成 3-5 趟车。

2.  **物理规则 (Physics & Naming):**
    * **G/C 高铁:**
        * 命名: G1xxx, C2xxx
        * 速度: ~300km/h (用于计算历时)
        * 车站优先: xx北, xx南, xx东 (高铁站)
        * 席位: 必须有 商务/一等/二等/无座；**严禁**出现硬卧/硬座。
    * **D 动车:**
        * 命名: D3xxx
        * 速度: ~200km/h
        * 席位: 二等/一等/无座；偶有软卧(D卧铺)。
    * **Z/T/K 普速:**
        * 命名: Z5, T109, K336
        * 速度: ~100-120km/h
        * 车站优先: 不带方位的城市名 (如 "西安" 而非 "西安北")
        * 席位: 必须有 软卧/硬卧/硬座/无座；**严禁**出现商务/一等。

3.  **时间计算公式:**
    * `Distance` = 随机生成两地距离 (500km - 2500km)
    * `Duration` = `Distance` / `Speed` (需转换为 HH:MM 格式)
    * `End_Time` = `Start_Time` + `Duration` (需处理跨天，如显示 "次日")

4.  **库存随机化:**
    * 状态随机分布在：'有', '无', '候补', 或具体数字 '1-10'。
    * 热门线路 (如 G字头) 的二等座容易出现 '候补'。

### C. 性能要求 (Performance Requirements)
* **批量插入:** 使用 SQLite 的 `Transaction` (事务) 进行批量插入，确保 5000+ 条数据能在 1秒内生成完毕。
* **索引优化:** 在 `from_city` 和 `to_city` 字段上建立索引，确保查询速度 < 50ms。


### 5. 补充接口：车站模糊搜索 (Station Search) - 🚨 修复前端报错
前端组件（CitySelect）依赖此接口进行车站查询。

* **Endpoint:** `GET /api/stations`
* **Query Param:** `search` (关键词，如 "sh", "上海")
* **Logic:**
    * 必须基于 `CITY_MAP` 数据源。
    * 如果 `search` 为空，返回热门车站（如北上广深）。
    * 如果有输入，按拼音或中文模糊匹配。
    * **数据格式:** 返回数组 `[{ name: "上海虹桥", code: "SHQ", pinyin: "shanghaihongqiao" }, ...]`

### 6. 服务器配置 (Server Config) - 🚨 架构适配
鉴于项目包含预览模式 (4173) 和开发模式 (5173)，后端必须适配：

* **Port:** 锁定 **3000**。
* **CORS (跨域配置):**
    * 必须允许 **开发环境** (`http://localhost:5173`)
    * 必须允许 **预览环境** (`http://localhost:4173`)
    * 建议直接设置为允许所有 (`origin: '*'`) 以避免本地测试麻烦。
* **Error Handling:** 增加全局错误捕获，防止因为某个接口报错导致整个 Node 进程退出（Server Crash）。

### 7. 启动与调试
* 启动命令: `node server.js`
* 成功标志: 控制台输出 `🚀 Server running on http://localhost:3000`

### 8. 强制有票策略 (Loose Data Strategy) - 🚨 修复无数据专用
为了确保演示效果，后端必须实现“无论搜哪天都有票”的逻辑：

1.  **移除日期过滤 (Remove Date Filter):**
    * 在执行 SQL 查询时，**只匹配** `from_city` (出发城市) 和 `to_city` (到达城市)。
    * **严禁** 在 `WHERE` 子句中包含 `date` 字段。

2.  **日期动态伪造 (Date Spoofing):**
    * 查询出结果后，在发送给前端之前，遍历所有车票数据。
    * 将每张车票的 `date` 字段，**强制修改** 为前端请求参数中的 `date` (例如 `req.query.date`)。
    * *效果：前端搜 12月11日，拿到的票就显示 12月11日；搜 1月1日，就显示 1月1日。*

3.  **兜底硬编码 (Hardcoded Fallback):**
    * 如果数据库真的为空（比如生成的城市不对），**不要返回空数组**。
    * 必须直接返回一个包含 3-5 条写死数据的数组（如 G1, Z5 等），确保页面永远有东西展示。
